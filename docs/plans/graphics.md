# Graphics, audio and UI

`@hxmc/os` (windows, input, the app loop, audio) and `@hxmc/gfx` (the GPU
layer and the shader macro) are built: their APIs are in
[packages/os/README.md](../../packages/os/README.md) and
[packages/gfx/README.md](../../packages/gfx/README.md), their tests in
[docs/testing.md](../testing.md), "Graphics". Back ends: GL/GLES 3 through
EGL on Linux (the glibc mode), Metal on macOS arm64, D3D11 on Windows,
WebGPU and WebGL2 in the browser; audio on ALSA, CoreAudio, WASAPI and
WebAudio. The UI toolkit is `@hxmc/ui` (its design: [ui.md](ui.md)); the web packages built on it are in [web.md](web.md).

## Principles

- Pure Haxe, no C library: back ends call the system APIs through externs
  (COM vtables, `objc_msgSend`, `dlopen`), shipped as source packages
  ([packaging.md](packaging.md)). API comparison (Kore 3, SDL3 GPU, sokol,
  WebGPU, bgfx): Kore 3 is the model (zlib; WebGPU-shaped, automatic
  tracking, small back ends), without its window/device coupling and
  `.kong` tools.
- GPU drivers (Mesa, NVIDIA) are glibc shared libraries a static musl
  executable cannot load: graphics on Linux uses the glibc mode
  (`-D hxmc.libc=glibc`; more modes in [targets.md](targets.md), "Linux").
- `@hxmc/os`: raw OS bindings (`hxmc.os.win32`, objc + AppKit, X11, later
  Wayland) plus windows, input and the app loop. The loop is callback
  driven (`App.run(onFrame, onEvent)`), since Cocoa, GTK and the browser
  own it; a `Surface` can be a window or a child of one (child HWND, NSView
  + CAMetalLayer, Wayland subsurface, canvas).
- `@hxmc/gfx`: WebGPU-shaped with integer handles, immutable pipelines,
  slot binding and `setUniforms` into a per-frame ring; automatic sync,
  two frames in flight, no allocation per frame; main thread only. Bind
  groups, compute (behind `device.features`) and threading later.
- Shaders are Haxe (`hxmc.gfx.shader`), against Heaps' hxsl: plain typed
  functions (inputs are parameters, outputs return values, no globals
  matched by name), compiled when the program is (no shader linker or
  compiler in the app), typed uniforms and layouts, the math runs on the
  CPU too, no engine.
- Back ends in order: GL, Metal, D3D11, WebGPU, WebGL2 (built), then
  Vulkan (SPIR-V from a Haxe emitter) and D3D12.

## How it is built

Decisions worth keeping, per back end (the code is the reference):

- Selection: back ends are chosen by `Mem.os()`, which the lowering folds.
  No field may have a back end's type (`hxmc.gfx.Impl` is an abstract over
  `Any`), or all its methods would be compiled and its libraries
  imported. On wasm32-wasi the choice is at run time: WebGPU when the
  JavaScript side has a device (requested before `main`), else WebGL2
  (forced with `browser.mjs`'s option `gfx: 'webgl2'`, the site's
  `?gfx=webgl2`).
- GL: GLES 3.0 through EGL, entry points through `eglGetProcAddress` as
  `@:hxmc.indirect` calls generated by a build macro (`Loader`); typed for
  wasm32-wasi, the same declarations become imports of the module
  `hxmc_gl`, which `packages/gfx/imports.mjs` implements on a WebGL2
  context (WebGL2 is GLES 3.0, so `GLBackend` runs unchanged).
- Metal: `hxmc.os.objc` calls `objc_msgSend` through its address as one
  `@:hxmc.indirect` extern per shape (the `Sender` build macro), makes
  classes at run time for delegates (`@:hxmc.callback` methods), and
  drains an autorelease pool per frame. `CocoaWindow` polls events with
  `nextEventMatchingMask:` and a past date, so the loop stays `App.run`'s
  (a display link would call back on another thread). Frameworks are
  imported by path; AppKit, whose classes are only found by name, through
  `NSApplicationLoad`. MSL is compiled at run time.
- D3D11: `Win32Window`'s window procedure is a `@:hxmc.callback`, the
  queue drained with `PeekMessageW` each frame; user32 calls run in a safe
  region, since most call the window procedure; the process is
  per-monitor DPI aware. COM through vtables (`Com`: `@:slot(n)`
  declarations in the headers' order become `@:hxmc.indirect` calls).
  `D3DCompile` from the system's d3dcompiler_47.dll; a flip-model swap
  chain; WARP when there is no GPU.
- WebGPU: one import per call with integer arguments; JavaScript objects
  live in `browser.mjs`'s handle table. `readPixels` cannot wait in a
  browser, so the JavaScript side reads asynchronously.
- Uniforms: GL two buffers bound by range, blocks bound to slots by name at
  link time (ES 3.00 has no `layout(binding)`); D3D11 constant-buffer
  offsets where 11.1 has them, else a dynamic buffer per slot (wined3d;
  `HXMC_GFX_D3D11_NO_OFFSETS=1`); Metal `setVertexBytes` (4 KB a block);
  WebGPU dynamic offsets into one buffer, a bind group per set of
  textures. Textures: GLSL `sampler2D` on unit n, WGSL `texture_2d<f32>` at
  binding n and its sampler at 16 + n, MSL `texture2d` and `sampler`, HLSL
  t<n> and s<n>.
- Conventions are WebGPU's, D3D's and Metal's (clip z 0..w, the fragment
  position from the top left, a texture's first row its top); the emitted
  GLSL maps clip z and flips `gl_FragCoord.y` with a uniform the GL back
  end sets (`u_target`); in a pass into a texture it flips the position's
  y instead (and GL's front faces turn clockwise), so that the texture's
  first row is the image's top there too.
- Textures: the formats every back end has (`TextureFormat`; RGBA16F and
  R32F render targets need GL's `EXT_color_buffer_float`, which WebGL2
  enables); GL's immutable storage (`glTexStorage2D`); R32F and depth
  textures are not filterable on GL ES and WebGPU, so they are read with a
  Nearest sampler and WebGPU's pipeline takes, at the first draw that binds
  one, a variant whose bind group layout reads them unfilterable (made
  once). A pipeline names its targets' formats (`colorFormat`,
  `depthFormat`): Metal and WebGPU bake them in. A pass into a texture is
  GL's one framebuffer object (attached anew when the textures change),
  D3D11's render target or depth-stencil view (unbound at the pass's end,
  so that the texture can be sampled), Metal's and WebGPU's attachments.
  Mip levels are generated by `glGenerateMipmap`, D3D11's `GenerateMips`
  (the texture a render target with `GENERATE_MIPS`), Metal's blit and on
  WebGPU a pass per level sampling the one before (imports.mjs, its views
  and bind groups made once per texture). `sample` in a fragment stage
  takes the derivatives' level (WGSL: the `derivative_uniformity`
  diagnostic off, as the other languages allow it in non-uniform control
  flow), `sampleLevel` a given one.
- The shader macro: a class implementing `Shaders` (Haxe runs build macros
  only from `@:build`/`@:autoBuild`, so an interface rather than
  metadata). Build time records each function as written; an expression
  macro in the class (`__shaders`) types them again with
  `Context.withOptions({allowInlining: false})`, so calls to the math types
  stay calls; `Lower` turns that typed AST into a small structured IR
  (`Ir.hx`), rejecting what shaders cannot do with its position; four
  emitters print it (HLSL's matrices transposed, MSL's uniform structs
  padded to std140). It adds about 0.27 s to a build (typing the macro and
  the math types' swizzles and overloads). The math types are inline
  abstracts over `@:hxmc.struct` values, so CPU math allocates nothing.

## Left

- Multisampling and its resolve (GL: a multisampled renderbuffer and a
  blit; Metal, WebGPU: a resolve texture of the pass; D3D11:
  `ResolveSubresource`; pipelines take a sample count on Metal, WebGPU and
  D3D11), several colour targets in a pass, passes with a depth target only
  (shadow maps), comparison samplers, anisotropic filtering, reading a
  render target back (WebGPU only asynchronously), cube and array
  textures, compressed formats (BC on the desktop, ETC2 and ASTC on
  phones: a capability query then).
- Bind groups (fewer calls than a slot each), compute.
- Shader macro: variants (compile-time constants per pipeline), integer
  vertex formats and flat varyings, `switch`, arrays of constant size,
  matrices other than 4x4, SPIR-V, caching emitted code across
  compilations (the compilation server).
- Instancing in the shader macro: instance attributes it lays out and
  writes itself (today a program splits the input struct's locations over
  two buffers in the pipeline's layout: examples/Instances.hx).
- Input methods: X11 (`XOpenIM`, `Xutf8LookupString`: variadic calls),
  Cocoa (`NSTextInputClient`).
- macOS: frames during a live resize (AppKit's tracking loop runs inside
  `sendEvent:`: a timer in the event-tracking run loop mode), a menu
  (Cmd-Q), x86-64 (`objc_msgSend_stret` for results over 16 bytes).
- D3D11: a lost device (`DXGI_ERROR_DEVICE_REMOVED` throws), the debug
  layer.
- WebGPU: shader compilation errors are only logged (asynchronous); node
  has no WebGPU (the corpus runner stays WASI only).
- WebGL2: `glGetString` (it would return memory), a lost context
  (`webglcontextlost`).
- Wayland, Vulkan, D3D12.

### Graphics in the playground

gfx programs in the site's playground: its compiler needs the packages'
sources in its bundle, the worker the packages' `imports.mjs` and a canvas
(an OffscreenCanvas, or the page's canvas driven from the worker's
module).

## UI

`@hxmc/ui` (with `@hxmc/text`, pure Haxe fonts and layout, and `@hxmc/view`,
markup with Solid-like signals): the core (tree, flexbox and grid layout,
events, focus), a drawn backend on gfx, native controls
(`hxmc.ui.native`), the platforms' accessibility, tested on Eval, natively
and in Chromium. Its survey and design: [ui.md](ui.md). What the renderer
needs from gfx is on main's API: `Device.writeTexture` of a region (a
glyph atlas uploads the part that changed), `destroyBuffer` and
`destroyTexture`; its atlas is RGBA8 (coverage in red, read at the nearest
texel), its clips in the shader (no scissor), its colours premultiplied
(`Blend.Premultiplied`). os's events were merged with ui's: characters are
`TextInput` events (strings, an input method's commits), the wheel
`Scroll` (pixels, as a browser's wheel event).
What comes after it: [web.md](web.md) (`@hxmc/view`, `@hxmc/web`, the
site) and Android's native controls ([targets.md](targets.md)).

Engines: a compatibility layer for HashLink's natives (`sdl.hdll`,
`directx.hdll`, `fmt`) on top of os and gfx would run Heaps unchanged.

## Frames in step with the display

- Frames driven by the display: `Choreographer` on Android, `CADisplayLink`
  on iOS and macOS, a waitable swap chain or `DwmFlush` on Windows,
  `requestAnimationFrame` in the browser. 120 Hz displays supported.
- To consider: a UI thread (input, signals, layout, recording draw
  commands) apart from a render thread (GPU submit and present), so a slow
  layout and a slow GPU frame do not add up. Measure whether it pays
  before committing: it touches the `hxmc.os` loop and who owns the
  `Device`.

The collector's side of a frame (collecting between frames, pause
budgets): [runtime.md](runtime.md#frames-and-pauses).

## Rendering capability

- **Partial redraw**: damage tracked per frame, only what changed redrawn,
  with the platform's present-with-dirty-rects where there is one.
  Measure power on a laptop and a phone.
- **Static subtrees cached as textures**, invalidated from the node tree.
- **Paths, strokes, blur** (`backdrop-filter`, shadows on any shape) and
  path clipping on the GPU, together with [document.md](document.md)'s
  Canvas work.
- **Shaders per node**: a node attaches a gfx shader to its paint, written
  in Haxe and compiled at build time like today's shaders, with its rect,
  states and tokens as inputs: effects a box, border and shadow model
  cannot express. Nodes without one keep the one-draw-call path.
- **Shaders compiled at build time, always**: no shader compilation (and
  its stutter) during a frame, by design; a test asserts that none
  happens.
- Later: Vulkan on Android, wide colour gamut and HDR.

## Audio

Output is built (`hxmc.os.audio`, packages/os/README.md: a pull model,
the callback on an audio thread of the runtime's, never a system thread,
which the runtime does not know). Left:

- Input (capture).
- Device choice and hot-plug (WASAPI's `AUDCLNT_E_DEVICE_INVALIDATED`,
  CoreAudio's default device changing).
- Formats other than float; PipeWire or PulseAudio directly.
- A real-time priority for the audio thread (`pthread_setschedparam`,
  MMCSS's `AvSetMmThreadCharacteristics`).
- An AudioWorklet over shared memory once wasm threads exist.
- A checked `@:hxmc.noGc` callback type for user code (the callback
  running on the system's thread directly).
