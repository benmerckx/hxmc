# 3D: `@hxmc/3d`, a scene layer for games

`@hxmc/gfx` is a portable GPU layer at about WebGPU's level (buffers,
textures, render targets, mips, pipelines, shaders written in Haxe) and
`@hxmc/os` gives windows, input, the app loop and audio. A 3D game needs
the layer above them: math that the CPU and the GPU agree on, a scene
graph, cameras, models loaded from glTF, lit materials, animation, input
mapped to actions, physics and tools. This plan is that layer:
`@hxmc/3d` (packages/3d), in seven steps, each useful on its own and each
proved by a demo on the site with golden images in CI. The design follows
a survey of the established engines ([Prior art](#prior-art)).

What is built so far is at the end ([Status](#status)).

## Principles

- **Layered on gfx, gfx unchanged.** gfx stays the low layer, with its own
  roadmap ([graphics.md](graphics.md#left)). `@hxmc/3d` is ordinary gfx
  code: the renderer records into the program's encoder, so a program
  adds its own passes, uses the scene graph with its own renderer, or
  drops to gfx for one effect. What 3d needs that gfx lacks
  (multisampling, depth-only passes, comparison samplers, cube textures,
  storage buffers) lands in gfx first, with gfx's tests; each step below
  names it.
- **One implementation of each thing.** One set of math types: gfx's
  shader types (`Vec2`, `Vec3`, `Vec4`, `Mat4`) are the CPU's too, so a
  matrix built on the CPU is the bytes a shader reads and a function
  written once runs on both; 3d adds only what shaders lack (`Quat`,
  `Aabb`, inverses). One renderer (no second pipeline for low-end or
  high-end), one material system, one glTF reader (the runtime's and the
  asset step's), one image decoder (`@hxmc/ui`'s, moved down when 3d
  needs textures), one loop (`hxmc.os.App`), one hot reload
  (`hxmc.dev.Hot`).
- **Small binaries.** A feature is code a program reaches or not: no
  central class that switches over every light, material or object type
  (three.js's and PlayCanvas's lesson), no side-effect registration
  (Babylon's), no reflection. Component stores exist only for the kinds a
  program uses; optional features are turned on explicitly
  (`renderer.use(Shadows)`, or a `-D`); the cost of each is measured
  ([Sizes](#sizes)) and the minimal app (a mesh, a camera, a light, the
  standard material) is measured in CI.
- **Fast builds.** No macro over user classes for the scene; the macros
  are gfx's shader macro (the package's few shaders, and materials'
  slots) and the optional asset step.
- **Every target.** Browser (WebGPU, WebGL2), Linux, macOS, Windows,
  Android, iOS: whatever gfx runs on, nothing per target in 3d. The
  renderer is mobile-first (forward, MSAA-friendly, no G-buffer) and
  keeps to what WebGL2 and GLES 3.0 can do, degrading (fewer cascades,
  no MSAA) rather than splitting.
- **Fast refresh of game state.** A world is flat data (transforms in
  arrays, components in stores), carried across a reload by
  `hxmc.dev.Hot` ([docs/dev.md](../dev.md)) like `@hxmc/view`'s signals:
  the player stays where they were. GPU resources are released in
  `Hot.onDispose` and made again by the new build; assets and pipelines
  are keyed so that they can be swapped in place.
- **No engine lock-in.** Nodes are handles with an ergonomic API, not a
  class hierarchy to extend; there is no ECS in the core (an optional
  package can key its components on the same node ids).

## Design

### Object model: handles over flat data

A `World` holds a scene graph of `Node`s. A `Node` is an `abstract
Node(Int)`: a generational handle (its world, a generation and a slot),
so nodes cost no object each and a disposed node's handle is detectably
stale. The world stores, per slot, the local translation, rotation and
scale, the local and world matrices, the parent and siblings, the name
and visibility, in flat arrays (Godot's servers, Filament's managers,
Fyrox's pools). World matrices are computed when asked and cached: a
slot keeps the version of its parent's matrix it was computed from, so a
still subtree costs nothing per frame (Bevy 0.16 reports about 10x from
skipping clean subtrees).

What a node carries (a mesh, a light, a camera, later a skin or a
rigid body) is a component in a typed `Store<T>` keyed by node, made the
first time its kind is used (`StoreKind<T>`, a static of the kind's
module), so a kind nobody uses is not linked and the renderer reads flat
lists rather than walking the tree.

Users see `node.position = new Vec3(0, 1, 0)`, `node.add(child)`,
`node.lookAt(target)`, `Camera.attach(node, camera)`. One difference
from the survey's sketch: `position` is a `Vec3` value, set whole, rather
than a reference with settable components (`node.position.x = 3`): gfx's
vectors are immutable values, and a second, mutable vector type would be
a second math library.

### Materials

- The default is glTF's metallic-roughness model (`Material`, glTF core
  semantics) plus an unlit one; each `KHR_materials_*` feature
  (clearcoat, sheen, transmission, ...) is an opt-in module adding fields
  and shader code only when used.
- Extension is by **typed slots**: a material type overrides named slot
  functions of the shading model (`surface(s:SurfaceInputs)`,
  `vertex(v:VertexInputs)`: Filament's `material()`, TSL's nodes), written
  as gfx shader code and composed **at build time** by the shader macro,
  which generates only the variants used (skinned or not, shadows,
  light-count buckets) behind a small variant key, plus the typed
  uniform writer. No string patching of shader chunks, no runtime shader
  compiler or linker (HXSL's cost), no global implicit names.
- Material types are pipeline families; material instances are data (a
  parameter block and texture indices). Each instance has an integer id:
  draws sort by it now, and it indexes a material buffer once gfx has
  storage buffers (bindless-ready).
- An escape hatch: a material with its own vertex and fragment stages
  that still receives the engine's typed inputs (camera, lights,
  transforms).

### The renderer

- **One renderer: clustered forward+**, mobile-first: an optional depth
  prepass per camera, cascaded shadow maps for the directional light and
  atlas shadows for spot and point lights, an HDR target then tone
  mapping, MSAA (FXAA without it).
- **Extract, then record.** The renderer extracts a flat draw list from
  the world (shown meshes inside the view, a draw per primitive, sorted
  by pipeline and material; transparent ones back to front), then records
  it. The list is the seam for automatic instancing (identical mesh and
  material), for threads, and for GPU culling and indirect draws later.
- **A small render graph**: passes declare what they read and write,
  unused passes are culled, transient targets reused, and on tile GPUs
  (Metal, GLES) load and store merged into one native pass. Built-in
  passes: shadows, depth prepass, opaque, sky, transparent, post (tone
  mapping, bloom, FXAA), an overlay hook. Programs add passes at named
  injection points (`BeforeOpaque`, `AfterOpaque`, `AfterTransparent`,
  `BeforePost`, `AfterPost`).
- **Multi-view from day one**: each camera of a world is a draw of its
  own (split screens, shadow views, XR's two eyes).
- **Features opt in**: shadows, a post effect, a material extension, a
  new renderable kind (particles, text, Gaussian splats) is a module the
  program names (`renderer.use(Bloom)`) or a `-D`; the renderer core
  knows none of them.
- Designed now, built later: per-instance and per-material data in GPU
  buffers where gfx has storage buffers (uniform blocks per draw on
  WebGL2 and GLES), a pipeline cache keyed by shader, variant and layout
  (shader hot reload), a `LightingEnvironment` (image-based light,
  spherical-harmonics probes, lightmaps) so better global illumination can
  plug in.

### Assets: glTF first

- **Runtime**: glTF 2.0 (`.glb`, `.gltf`): core materials, skins, morph
  targets, animations, then `KHR_mesh_quantization`,
  `KHR_texture_transform`, `KHR_materials_emissive_strength`,
  `KHR_lights_punctual`, `KHR_materials_unlit`. Optional modules:
  `EXT_meshopt_compression` (preferred), `KHR_texture_basisu`, the
  `KHR_materials_*` set, `KHR_gaussian_splatting`; Draco only as a
  separate opt-in. Extensions register handlers (Bevy's
  `GltfExtensionHandler`); the reader's core knows none of them.
- **Per-file references, no global `Assets` module.** `Model.of("models/hero.glb")`
  (and `Texture.of`, `Sound.of`, ...) is an expression macro: it checks
  that the file exists, reads the glTF's structure when compiling and
  types the result from it (`hero.nodes.LeftHand`, its meshes,
  materials and animations, so a typo is a compile error, as gltfjsx's
  output but checked), and registers the file for the build's asset
  packing. Only referenced files are packed; packing is where baking
  happens: vertex data interleaved and quantized for the renderer,
  meshopt simplification, textures transcoded per target (ASTC on
  phones, BC on desktops, KTX2 on the web) so no transcoder ships
  natively, environment maps prefiltered.
- **Loading hidden for static references.** The compiler knows every
  referenced file. In the browser the loader fetches them all in
  parallel with the wasm module's download and compilation, before
  `main`, so `Model.of` returns a ready model synchronously; tiny files
  may be embedded in the module. Natively, on Android and iOS the files
  ship beside the binary or in the APK or bundle and are read
  synchronously.
- **Escape hatches.** `Model.of(path, Lazy)` gives a handle and a ready
  signal (big games, loading screens); `Model.load(runtimePath)` is
  asynchronous, for paths known only at run time. Both are `Asset<T>`
  handles with an observable `state` (Loading, Ready, Failed) and
  `then`, reference counted with a leak report in debug builds; hot
  reload swaps the data behind the same handle, so every user updates.
- In dev the files are served raw and reloaded on change; a release packs
  them. Built today: `Asset.embed(path)` (a file's bytes in the program)
  and a first `Model.of` (below, [Status](#status)).

### Loop, input and a reactive layer

- Ordered frame stages (`Input`, `FixedUpdate`, `Update`, `LateUpdate`,
  `PreRender`) on top of `App.run`; `FixedStep` gives the fixed update's
  rate and the interpolation factor.
- The reactive layer is an optional package, `@hxmc/3d-ui`, on
  `@hxmc/view`'s markup macro: tags map to the core's typed constructors
  when compiling (only the node types used are linked), signals bind per
  property (no reconciliation), per-frame work goes through the frame
  stages, pointer events through a raycast picking module. The core
  exposes what it needs and nothing reactive: property setters,
  add/remove/dispose, the stages, picking.

### Out of the core

Visibility buffers, mesh shaders, virtual geometry, hardware ray tracing
and ReSTIR, Lumen-style global illumination, neural rendering, a USD
runtime, physics (a separate package: step 6), and runtime shader
compilation in release builds.

## The steps

### 1. Math, the scene graph, cameras and a loop

- Math: gfx's `Vec3`, `Vec4`, `Mat4` with `ShaderMath`'s builtins;
  `Quat` (axis-angle, Euler, from a matrix, product, rotate, slerp),
  `Aabb` (union, transform, contains, intersects, ray), `MathTools`
  (inverse, determinant, transpose, compose and decompose, lookAt,
  lookRotation, normal matrix).
- The world and its nodes as above; components in stores; `Camera`
  (perspective or orthographic, view, projection, rays for picking) as a
  component; `FixedStep`.
- Hot: a world's transforms and the clock save and load by key.
- Demo: a hierarchy of moving parts; golden image native and in the
  browser.

### 2. glTF 2.0

- `Gltf.parse(bytes, ?resolve)`: .gltf (buffers as `data:` URIs or files
  `resolve` returns) and .glb, into a typed, checked `GltfDoc` (indices
  in range, views inside buffers, accessors inside views, no cycles), no
  `Dynamic` past the reader; accessors of every component type,
  normalized, strided; sparse accessors next.
- `GltfNodes.build(doc, world, ...)`: the hierarchy (TRS or matrices,
  cameras), each instantiation a prefab copy; `GltfScene`: the GPU meshes
  and materials made once, instantiated into worlds.
- Images (PNG, JPEG) through the decoders `@hxmc/ui` has, moved to a
  package both use; extension handlers; the asset step above.
- Demo: a small model generated by a script in the repository (MIT),
  loaded and drawn; its structure tested against the generator's.

### 3. Lit rendering

- The standard material: Cook-Torrance (GGX, height-correlated Smith,
  Schlick), base colour and emissive in linear light, tone mapping (ACES
  or Khronos PBR Neutral), sRGB textures decoded by the sampler
  (`RGBA8Srgb`).
- Lights: directional, point and spot (`KHR_lights_punctual`), clustered;
  a sky-and-ground ambient, then image-based light and a skybox from an
  environment (prefiltered at build time or at load on the GPU).
- Shadows (needs gfx's depth-only passes and comparison samplers), MSAA
  (gfx's multisampled targets), instancing (gfx's `step: Instance`).
- The render graph and its injection points.
- Demo: the glTF scene lit, shadowed, tone mapped.

### 4. Input actions

- `Actions`: named actions bound to keys, mouse buttons, gamepad buttons
  and axes and touch regions, as buttons (pressed, held, released this
  step) or axes (1D, 2D for sticks and virtual sticks), read once per
  fixed step; bindings are data (rebinding at run time).
- Gamepads need `@hxmc/os`: XInput, GameController.framework, evdev,
  Android's input events, the browser's Gamepad API.
- Demo: a character moved by keyboard, gamepad or a virtual stick.

### 5. Animation

- Keyframe clips (glTF's translation, rotation, scale and weights; step,
  linear, cubic spline), sampled into the world's transform arrays,
  blended (cross-fades, additive layers) by an `Animator`.
- Skinning: joints and inverse bind matrices from glTF, joint matrices
  in a uniform block or a texture, four weights a vertex, a shader
  variant. Morph targets after.
- Demo: a skinned character walking.

### 6. Physics: `@hxmc/physics`

A separate package (the core never depends on it), keyed on the same
node ids:

- first a small built-in core: shapes (sphere, box, capsule, convex hull,
  a triangle mesh for level geometry), a broad phase, contacts, a
  sequential-impulse solver with sleeping, raycasts, a character
  controller, at the fixed step;
- later a binding to an established engine (Jolt, or Rapier) behind the
  same `PhysicsWorld` API, its size out of programs that do not use it.
- Demo: boxes falling on a level, shot with raycasts.

### 7. Tooling

- A debug overlay drawn with `@hxmc/ui` over the frame: frame times (CPU,
  GPU where gfx exposes timestamps), draws, triangles, the world's tree
  to inspect and edit transforms, toggles (wireframe, bounds, cascades).
- An editor later, from the same pieces, saving scenes as glTF plus a
  small override format (prefabs with overrides).

## Testing

Each step gets the lanes gfx has ([docs/testing.md](../testing.md),
"Graphics"):

- `make 3d-check`: the unit tests (math, the scene graph, cameras, the
  clock, the glTF reader) on Eval, natively and as wasm32-wasi, then the
  renderer's frames headless against golden images on llvmpipe
  (packages/gfx's rule: `GfxTest.compareBytes`), in CI's `gfx` job.
- `make 3d-web-check`: the same frames on WebGPU and WebGL2 in headless
  Chromium (packages/gfx's `compare.mjs`), also in the `gfx` job.
- The same frames on Linux ARM64 (llvmpipe) and Windows x86-64 and arm64
  (D3D11's WARP) in gfx's jobs (`make 3d-programs`); Metal, Android and
  iOS later (the programs build for them today).

## Prior art

From a survey of three.js and TSL, react-three-fiber and drei, Babylon.js,
PlayCanvas, Bevy, Fyrox and three-d, Godot, Unity's SRP, Unreal (RDG),
raylib, Filament, Ogre-next, Heaps and HXSL, Armory and Kha, SceneKit and
RealityKit, and newer work (GPU-driven rendering, Gaussian splats, WebGPU
bindless, data-oriented scenes, declarative 3D), October 2026. What this
plan takes, and from where:

| Concern | Taken | From |
| --- | --- | --- |
| Object model | a handle arena with flat transforms and typed component stores; ergonomic handles; an optional ECS outside the core | [Godot's servers](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html), [Filament](https://google.github.io/filament/Filament.html)'s managers, [Fyrox](https://fyrox.rs)'s pools; [Bevy 0.16](https://bevy.org/news/bevy-0-16/)'s skipped clean subtrees |

| Reactive layer | optional; markup to typed constructors; a signal per property; ordered frame tasks | [react-three-fiber](https://r3f.docs.pmnd.rs/getting-started/introduction), [Threlte](https://threlte.xyz), [solid-three](https://github.com/solidjs-community/solid-three) |
| Size | explicit opt-in features, no side-effect imports, no runtime shader compiler, the minimal app measured | three.js's tree-shaking reports ([1](https://discourse.threejs.org/t/what-is-the-state-of-tree-shaking/33168), [2](https://discourse.threejs.org/t/tree-shaking-three-js/1349?page=3)), Babylon's [ES6 packages](https://doc.babylonjs.com/setup/frameworkPackages/es6Support), [sokol](https://github.com/floooh/sokol), [Godot's size options](https://docs.godotengine.org/en/stable/contributing/development/compiling/optimizing_for_size.html) |
| Designed for, later | GPU-resident instance data, bindless-ready indices, extension registries | [WebGPU's bindless proposal](https://github.com/gpuweb/gpuweb/blob/main/proposals/bindless.md), Bevy's GPU-driven rendering |

Pitfalls taken as rules: no central class that knows every subtype; no
two parallel systems during a migration; small, explicit variant keys
(variant counts reported when compiling); pipelines warmed for loaded
assets (no first-use hitch); glTF as the contract, not one DCC tool; no
per-frame allocation of math values; forward and MSAA on tile GPUs.

Where this plan differs from the survey: assets are referenced per file
(`Model.of`, typed from the file) instead of through a generated global
`Assets` module; node positions are `Vec3`
values set whole (above, "Object model"); the Haxe package is
`hxmc.scene` rather than `hxmc.three`; and the loop stays `hxmc.os.App`
with 3d's stages on top, rather than a second `App`.

## API sketches

Built (see packages/3d/README.md):

```haxe
import hxmc.gfx.*;
import hxmc.gfx.shader.Vec3;
import hxmc.os.*;
import hxmc.scene.*;
import hxmc.scene.gltf.*;
import hxmc.scene.math.*;
import hxmc.scene.render.*;

class Game {
	static function main() {
		var window = new Window("Game", 1280, 720);
		var device = Device.create(window.surface);
		var renderer = new Renderer(device);
		var world = new World();

		// a model built into the program, made for the GPU once, instantiated
		var level = new GltfScene(Gltf.parse(Asset.embed("level.glb")), device);
		level.instantiate(world);

		var sun = world.node("sun");
		Light.attach(sun, Light.directional(new Vec3(1, 0.95, 0.9), 3));
		sun.rotation = Quat.fromEuler(-0.9, 0.4, 0);

		var eye = world.node("eye");
		var camera = Camera.attach(eye, Camera.perspective(Math.PI / 3, 0.1, 200));
		eye.position = new Vec3(0, 2, 6);
		eye.lookAt(new Vec3(0, 0, 0));

		var player = world.root.find("player");
		var step = new FixedStep(1 / 60), last = Sys.time();
		App.run(() -> {
			var now = Sys.time();
			step.advance(now - last, dt -> player.rotation = player.rotation * Quat.axisAngle(new Vec3(0, 1, 0), dt));
			last = now;
			var enc = device.beginFrame();
			if (enc == null) return;
			renderer.draw(enc, world, camera);
			device.endFrame();
		}, e -> if (e.kind == Close) window.close());
	}
}
```

// materials: typed slots composed by the shader macro when compiling
@:material(Standard)
class Dissolve extends MaterialExt {
	@param var noise:Texture2D;
	@param var threshold:Float = 0.5;
	@param var edge:Vec3 = vec3(1, 0.4, 0);
	override function surface(s:SurfaceInputs) {
		var n = sample(noise, s.uv0).x;
		if (n < threshold) discard();
		s.emissive += edge * smoothstep(threshold, threshold + 0.05, n);
	}
}

## Status

Built on the `scene3d` branch, each piece tested by `make 3d-check`
(unit tests on Eval, natively and as wasm32-wasi; frames against golden
images on llvmpipe), `make 3d-web-check` (the same frames on WebGPU and
WebGL2 in Chromium, as linear-memory wasm and as WasmGC) and measured by `make 3d-sizes`, all in CI's `gfx`
job; the frames also on Linux ARM64 (`gfx-arm64`) and on D3D11's WARP on
Windows x86-64 and arm64 (`gfx-windows`), and under Wine locally
(`check.sh`).

- **Step 1.** The math (`Quat`, `Aabb`, `MathTools` on gfx's types); the
  handle-based world (`World`, `Node`, `Store`, `StoreKind`); `Camera` as
  a component (rays for picking: `Pick.ray`, the nearest mesh node whose
  bounds a ray crosses, checked in the `instances` frame); `FixedStep`; `Stages` (Input, FixedUpdate, Update,
  LateUpdate, PreRender); `HotWorld` (a world's transforms carried across
  a reload by node path; the examples keep their clock and camera under
  `hxmc dev`); `Shapes`; `examples/Orbits.hx` (`SceneTest`, `orbits.png`).
- **Step 2.** `Gltf.parse` (.gltf, .glb) into a checked `GltfDoc`: meshes,
  materials, textures, samplers, images, nodes, scenes, cameras,
  `KHR_lights_punctual`, animations, skins; `GltfNodes`, `GltfScene`
  (made once, instantiated into worlds); textures of every map, read
  through glTF's samplers (filters, mip filters, wraps), decoded
  by a decoder the program names
  (`Images.decode`: `@hxmc/ui`'s PNG and JPEG decoders, no second
  implementation), mip-mapped. `Model.of(path)`: the file checked and its
  node, mesh, material and animation names typed when compiling (a typo
  is a compile error, tested); files up to 64 KB built into the program
  (`-D hxmc.scene.embed=<bytes>`), larger ones copied beside it
  (`assets/`, listed in `<output>.assets.json`): natively read from
  beside the executable, in the browser fetched by `@hxmc/os`'s
  `browser.mjs` before main, in parallel with the module's download, and
  served read-only through WASI (`options.assets`), so `Model.of` stays
  synchronous (tested: every scene in the browser from fetched files,
  natively the skinned one); Android and iOS still embed (their bundles'
  assets next), and per-target packing is next. `Model.of(path, Lazy)`
  (an `Asset` of the typed model, loaded in the background) and
  `Model.load(path)` (a path known at run time) through `@hxmc/os`'s
  `Fetch` (the browser's fetch, polled; natively the file at once);
  `Asset` handles (Loading, Ready, Failed; `then`, `onChange` for a
  swap) advanced by `Assets.poll` in `Stages.frame` (`lazy.png` is
  `skin.png`, natively and in a browser window). The asset step's first
  form: `hxmc.scene.gltf.Pack` (run at build time on Eval with the
  runtime's reader) and `PackedModel` (read without JSON; format 2:
  meshes in the renderer's layout with joints, weights and tangents
  computed at build time, materials with their maps and sampler, the
  images as the file has them, cameras, lights, skins, animations;
  `packedskin.png` is `skin.png`, `packednormals.png` is `normals.png`). Four generated
  samples, MIT (`packages/3d/test/SampleModel.hx`): `sample.glb` (17 KB:
  every index size, interleaved and normalized accessors, a node matrix,
  an animation of each interpolation), `skinned.glb`, `textured.glb`,
  `normals.glb` (`GltfTest`; `gltf.png`, `textured.png`, `packed.png` is `gltf.png`).
- **Step 3.** `Renderer`: extract into a draw list sorted by pipeline,
  material and primitive (frustum culling; runs of one primitive drawn
  instanced: `PbrInstancedShader`), record one pass; see-through
  materials (`material.blend`, glTF's alphaMode BLEND) after the opaque
  ones and the AfterOpaque hooks, farthest first, blended, depth not
  written (their pipelines made when first drawn); the world's first
  directional light and up to four point or spot lights; `PbrShader`
  (metallic-roughness: GGX, Smith, Schlick; a sky-and-ground ambient with
  an analytic split-sum; ACES; sRGB); optional features through
  interfaces, linked only when used (`RenderFeature`): `Shadows` (R32F
  maps, 3x3 PCF; gfx has no depth-only passes yet: one fitted to the
  casters, or two cascades, the first over the camera's view up to a
  split distance, moved by whole texels, the second the whole scene's),
  `Skinning`, `NormalMaps` (tangent-space normal maps through
  `PbrNormalShader`: tangents in a second vertex buffer, so the standard
  layout is unchanged and a program without the feature draws the same
  primitives without their maps; the file's tangents, else computed from
  the uvs when loaded, the computation linked only with the feature),
  `Sky`, `Environment` (an equirectangular image, its mip levels made on
  the CPU so every GPU reads the same texels, drawn behind the scene and
  lighting it: diffuse from a small level along the normal, specular
  along the reflection from a level by roughness; the shaders' missing
  inverse trigonometry as polynomial fits), `Particles` (a renderable kind: `Emitter` components
  simulated at the fixed step from their own seeds, drawn as instanced
  camera-facing quads, additive, at AfterOpaque); injection points (`renderer.inject(BeforeOpaque |
  AfterOpaque | AfterPass, f)` with `FrameInfo`), the render graph's
  first form. Frames: `gltf`, `shadows`, `instances` (169 nodes in two
  draws, checked), `spot`, `sky`, `particles`, `skin`, `textured`,
  `blend`, `cascades`, `environment` (`panorama.png`, generated), `normals` (a fourth sample, `normals.glb`: the cube with a normal map
  and no tangents; `GltfTest` checks the computed tangents and their
  handedness).
- **Step 4.** `Actions`: named actions bound to keys, mouse buttons,
  screen regions and key axes, read per step (a tap within a step
  counts), rebinding (`InputTest`); gamepads: `hxmc.os.Gamepads` (the
  standard layout; the browser's Gamepad API, Linux's joystick devices
  and XInput on Windows, polled by `Stages.frame` once the program called
  `Gamepads.enable()`, so others link none of it; macOS and the phones not yet; `Gamepads.set` feeds a pad from the
  program: on-screen sticks, tests) and the bindings `PadButton`, `PadAxis`
  (a dead zone; `InputTest` through a fed pad).
- **Step 5.** `AnimationClip` (translation, rotation, scale; step, linear
  with slerp, cubic spline), `Animator` (play, loop, speed, cross-fade);
  skinning (`Skin` per instance, joint matrices in an R32F texture read
  by `PbrSkinnedShader`, four joints a vertex; skinned casters in the
  shadow map through `ShadowSkinnedShader`, made only when shadows are
  used too; `skin.png`). Morph targets: glTF's targets (positions,
  normals) and weights (the mesh's, a node's, an animation's weights
  tracks: `MorphWeights`), blended on the CPU into each instance's own copy
  of the vertices when the weights change (`Morph`; `morph.glb`,
  generated; `morph.png`; packed too: `packedmorph.png` is `morph.png`).
- **Step 6.** `@hxmc/physics` (packages/physics): `PhysicsWorld`, `Body`
  (position, orientation, inertia from the shape), spheres, boxes and
  capsules moving and tumbling against each other and planes (box against box
  by separating axes among their faces' normals, the corners where the faces
  overlap: crates of one size stack, edges crossing get one contact midway; capsules as spheres
  at their segments' nearest points; `rotates = false` keeps a
  character's capsule upright; `Character`: a walking capsule steered
  towards a wanted velocity, grounded by a ray, jumping, climbing steps up to `stepHeight`; joints:
  `Joint.ball` (the two points one, the 3x3 effective mass inverted) and
  `Joint.distanceOf` and `Joint.hinge` (a ball joint keeping an axis each
  lined up), solved with the contacts: a pendulum swings at its period, a
  chain hangs, a door swings on its hinge), sequential
  impulses at contact points, accumulated and clamped, a sweep-and-prune
  broad phase (pairs in a fixed order: the same results), restitution,
  friction, sleeping, raycasts, bodies moving their nodes; deterministic
  on Eval, natively and as wasm32-wasi (a checksum, tested);
  `examples/Falling.hx` (`PhysicsTest`, `physics.png`), `examples/Walker.hx`
  (a `Character` among crates, drawn with `Shapes.capsule`; `walker.png`),
  `examples/Chains.hx` (chains on distance joints, a ball on a ball joint
  through them; `chains.png`).
- **Step 7.** `FrameStats` and `Overlay`, a debug overlay drawn with
  `@hxmc/ui`'s drawn renderer in its own pass (frame times as bars, draws,
  and the figures in a pixel font of its own: no font file, the same
  pixels on every machine) (`@hxmc/ui` and
  `@hxmc/text` needed only where used); the Orbits example shows it
  (`overlay.png`).

- **The reactive layer.** `@hxmc/3d-ui` (packages/3d-ui), a prototype:
  `SceneRenderer`, `@hxmc/view`'s renderer contract on the world (node,
  mesh, light, camera elements; properties bound to signals set the
  node's value, no reconciliation; `Show` and `For` add, remove and move
  subtrees), tested natively (`SceneUiTest`). Properties by name for now;
  typed constructors per tag next. A finding: hxmc does not yet pass a
  closure returning a struct value where a function of another type is
  expected (`memo(() -> new Vec3(...))` does not compile, a bare function
  bound as an attribute fails its cast), so such properties are bound
  through a `Signal`.

Shadows (`Shadows.cascaded`'s fitting too), skinning, normal maps and
the environment are features the program turns on, through
interfaces, so their code and shaders are linked only when used. The
renderer's share is mostly its shaders (the standard and the instanced;
on wasm32-wasi each in WGSL and GLSL, chosen at run time). The glTF
level includes the sample itself (about 23 KB as a base64 string) and
`haxe.Json` with `Reflect` over `Dynamic`; the asset step removes it:
the same scene packed at build time (vertex data already in the
renderer's layout, shared data written once: 16.1 KB against the .glb's
17 KB, its animations included) draws the same frame from a program
about 73 KB smaller natively and 56 KB smaller as wasm32-wasi (the
packed reader's lights, skins, images and samplers cost some 30 KB of
the 99 KB the first packed form saved). The world's 31 to 37 KB (its arrays and
generic stores) is the next thing to trim.

Not yet: alphaMode MASK (drawn opaque: gfx's shaders have no discard), order-independent transparency, normal maps on skinned and instanced draws, MikkTSpace's exact
tangents (Lengyel's are computed), glTF samplers per map (one a material: its base colour's) and wrapS differing from wrapT, more than two shadow cascades, MSAA (gfx first), clustered lights,
the render graph's passes and resources, properly filtered environment maps (a mip chain stands in) and HDR images, gamepads on macOS and the phones, hinge limits and motors, morph targets on the GPU, box edge-against-edge axes, the overlay's scene tree, assets in APKs and app bundles, `@hxmc/3d-ui`'s typed elements, an editor.

Findings for the compiler: a struct value (`Mat4`, `Vec4`) returned by
an interface method was taken for another struct type ("the struct
Mat4Data used as the struct Vec4Data", in `Renderer.writeFrame`; worked
around by returning an object, `RenderFeature.ShadowFrame`); and a closure
cannot capture a local of a struct type (`Vec3`, `Quat`, `Mat4`: their
memory is in the frame), so game code written as closures over the app
loop copies components into locals (examples/GltfViewer.hx). Lifting
such captures into the closure's environment would remove the
workaround.
